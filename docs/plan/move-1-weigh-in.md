# Move 1 runbook: Weigh-In

Weigh-In 1.2.0 moves from `Wet-Ink-Corporation/weigh-in` into this repository and ships as `rk-weigh-in` 2.0.0. On the way, `redkiln-core` is extracted from its store, and `weighin-contract` and `knowledge-contract` are born. It is the first move, so it also gives the SPEC its first code and this repository its first binary, plugin, release workflow and conformance fixtures.

This runbook makes the migration plan's eight steps concrete for Weigh-In. It does not re-plan: the end state is `references/docs/weigh-in.md` (crates, events, surfaces) and `references/docs/blueprint.md`, the formats are `spec/`, and the rules are `AGENTS.md`. Where this file names a choice those leave open, it says whether it is a two-way default or a call for Ryan.

Facts below were checked on 2026-11-01 against weigh-in `main` at `8587f57` (tag `v1.2.0`), weigh-in-plugin `main` at `7db2726`, and redkiln `main` at `a32e1d9`.

## Decisions before the import

Move 1 cannot start its code until the one-way and H-16 items here are decided. Each has a recommendation.

| # | Call | Door | Recommendation |

| M1-A | **Identity of weigh-in 1.x events on import** (SPEC JR-07 leaves it to Move 1). A 1.x event can reach a 2.0 store twice: from a ledger and from a committed journal written from it, or from two journals. weigh-in 1.x counts an event once by its canonical JSON (`journal.rs`, `stats`) | One-way (OW-6 territory: identities are kept forever) | **Content identity for every 1.x event.** Origin store id: the first 32 hex of `sha256("weighin-1x")`; position: the first 16 hex of `sha256` of the event's canonical 1.x JSON, as a `u64`. The same 1.x fact gets one identity on every machine, whichever source it came from, so imports on two clones agree and exchange journals without double counting. ST-15 then says "a weigh-in 1.x ledger maps as JR-07 says" instead of "origin is the old store's id and position" (a two-way SPEC edit). Alternative: ST-15 as written for ledgers, plus a per-file synthetic origin for journal lines and a content check before ingest; it is simpler to read but gives one fact two identities when a ledger and its journal meet on different machines. ## Release and cutover

2.0.0 is a release, so the release PR and the tag are Ryan's (charter; project rules). The first release here also creates what weigh-in's release workflow did:

1. **A release workflow** (`release.yml`, written in this move): tests, builds Linux musl and gnu, Windows msvc and gnu and macOS, packages `plugins/weigh-in/` and `plugins/mod/` with their `libexec/` builds, publishes the GitHub release from `plugins/weigh-in/CHANGELOG.md`'s section under `rk-weigh-in--v2.0.0` (the `release-tags` ruleset protects it), stamps the Cowork fetch script, and pushes the assembled marketplace to the release repository.
2. **The release repository** (wi-f041fb, org-sync spike): `weigh-in-plugin` becomes the suite's, holding every `rk-*` plugin as `./plugins/<name>` in one `marketplace.json`, with Sync automatically on. weigh-in pushes with a deploy key (`WEIGH_IN_PLUGIN_DEPLOY_KEY`); this repository uses a GitHub App token instead (wi-31aa59, a default).
3. **The release environment** with Secret Protection bought for this repository (wi-620988, deferred to this step).
4. **The last 1.x release** from weigh-in (1.3.0) prints a one-line SessionStart notice naming `rk-weigh-in` (plan step 8). It is a release too, and comes after 2.0.0 is installable.
5. **Archive** weigh-in with a last commit pointing its README and marketplace at `rk-weigh-in`; transfer the open issues first (plan step 7).

Owner-only steps in this list, for Ryan's sitting: rename `weigh-in-plugin` (and update its Customize > Plugins entry if the rename breaks it), turn on Sync automatically, create the App or token for the release push, the release environment and its reviewers, Secret Protection, transferring issues if the agent token cannot, and archiving weigh-in. Each gets a paste block when its turn comes.
