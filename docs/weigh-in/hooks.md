# Hook rules for `plugins/weigh-in/`

Weigh-In's hooks ship in Move 1, before the SPEC's fuller hook section, which arrives with Move 2 (field guide [T3](../guide/README.md#tensions-with-the-plan); Move 1 step 9, #24). Until then these are the plugin's charter rules: SPEC CLI-09 to CLI-11 as written (`spec/cli.md`), and the field guide's [HK-2](../guide/hooks.md#hk-2-never-off-without-a-word) and HK-4 to HK-8 adopted for this plugin. The SPEC wins where the wording differs, and Move 2 lifts the HK rules into it. The `weighin` crate charter (`crates/weigh-in/weighin/AGENTS.md`, Hooks) carries the short form; this page has each rule, how Weigh-In meets it today, and what is not yet met.

Weigh-In's hooks are all observers: SessionStart primes, Stop and SubagentStop capture `weigh-in` blocks, and PostToolUse scans what `Write`, `Edit` and `MultiEdit` wrote and recalls decisions anchored at that file (`hooks.json`, `src/hooks.rs`, behind the adapter `src/harness/claude_code.rs`). None is a guard or a gate. A rule that speaks of guards, denies or Stop gates binds any such hook the plugin adds; it is written here so the hook arrives already under it.

## The rules

**CLI-09. Exec form, `hook <event>`, fail open.** As written: "A hook is `<binary> hook <event>`, called by path in exec form from `hooks.json` (`${CLAUDE_PLUGIN_ROOT}/libexec/<binary>`), never through a shell. Hooks fail open: a hook notes its failure in its output, or in one stderr line when stdout cannot be written, and exits 0, even on a bug. Its usage errors still exit 2, so a test runs every `hooks.json` entry's arguments through the binary."
- *Met:* exec form by path, `hook <event>` on every entry, exit 0 even on a panic (`run_hook_guarded`), usage errors exit 2 (clap). `cargo xtask plugins` checks exec form, the launcher copy and `hook` as the first argument. `every_hooks_json_entry_is_hook_event_runs_and_never_blocks` (`tests/it/cli.rs`) checks that every entry's args are `hook <event>` and runs each through the binary with its event's payload. Step 9 made Stop, SubagentStop and PostToolUse pass their event name; the binary dispatches the event the payload names (`hook_event_name`), and the name on the command line sets the stdin cap (HK-6) and stands in when the payload names none (B-16).
- *Met* (step 6b), as decision D2 B reads "notes its failure in its output" until Move 2's hook section: every failure is still logged, and Stop, SubagentStop and PostToolUse add one sentence to their `systemMessage` (`Weigh-In: the <Event> hook failed, so capture may be off: <first failure>. Logged in <path>.`, or `It could not be logged: <why>.`) when the log held nothing unreported before their first failure, when a failure could not be logged, or in Cowork. Later failures in the session are only logged, and the next SessionStart counts them (HK-2), so a broken store says so once, not on every edit. SessionStart notes directly only what it could not log, since its report reads the rest back; one whose input is over its cap or not JSON dispatches nothing, so no report runs, and it notes as a turn does. Other events, and none, are only logged. A stdout that cannot be written is logged and told in one stderr line, `weighin: error: hook <Event> could not write its output: <error>` (CLI-08's form), and the hook still exits 0 (`hooks/failures.rs`, `harness/claude_code.rs`, `respond`; `tests/it/hook_notes.rs`). Output failures are logged anywhere a log can be written; input and parse failures only inside a git repository; in Cowork hooks write nothing to disk.

**CLI-13. Harness protocol at the edge.** Hook payloads and responses, transcript formats and `CLAUDE_*` variables are read and written in one adapter module per binary (root `AGENTS.md`, CLI first, harness second).
- *Met* (Move 1 step 6a): `src/harness/claude_code.rs` reads the payload into `hooks::HookInput`, runs the hook, and renders its `hooks::HookOutput` per event; `hooks`, `recall`, `env` and every command take plain values, and output is byte for byte what it was (every end-to-end hook test unchanged, render goldens per form). `cargo xtask plugins` fails on the protocol's tokens in any `.rs` file under `crates/` outside a binary's `src/harness.rs` and `src/harness/`, its integration tests, comment lines and a top-level unit test module as rustfmt writes it (`tools/xtask/src/harness.rs`). The other side of the edge, prompts naming only commands the CLI has: since step 6e it also fails on a skill, agent or command that names a `weighin` subcommand clap does not accept, read from code spans after the binary, its `libexec/` path or the skill's `W` alias (`tools/xtask/src/plugins/commands.rs`, against `weighin_contract::cli`, which weighin's `cli_pin` test pins against clap). *Residual:* the mod's argv arrays in TypeScript are not read; its own plugin tests pin them.

**CLI-10. A guard fails closed.** It denies what it cannot judge with a deny decision on stdout and exit 0, and exits 2 with one stderr line only when it cannot write that decision.
- *Not applicable today:* Weigh-In ships no guard. A guard added later declares `onFailure: "block"` and carries a manifest test for it (field guide HK-1).

**CLI-11. No build, no block.** With no `weighin` build present at all, the launcher copies (`libexec/weighin`, `libexec/weighin.cmd`, from `tools/launcher/`) let every hook through, and `hook SessionStart` says once that the plugin is off (not in Cowork).
- *Met on Linux and macOS* by the sh launcher and its tests (`sh tools/launcher/test.sh`).
- *Not met on Windows.* An exec-form hook there resolves `libexec/weighin` only to `libexec/weighin.exe`, a build packaged at release (M1-E). A `.cmd` cannot be spawned that way (`EINVAL`, B-16), so `weighin.cmd` serves calls through a shell, such as the skill's, and never a hook. With no build at all there is no `.exe`: the spawn fails with `ENOENT`, no launcher runs, and no "off" message is printed. Claude Code reports a hook error, so the plugin is not off silently, but CLI-11's promise does not hold. A guard declared `onFailure: "block"` may then block every call; whether `onFailure` fires on a failed spawn is unverified (M1-E, field guide T9). Weigh-In has no guard, so it is not exposed, but a guard must not be added here until this is settled.

**HK-2. Never off without a word.** Every hook error is appended to `hook-errors.log` in the state dir (`<git-common-dir>/redkiln/weighin/`), and the hook exits 0. The next SessionStart counts the lines past the offset in `hook-errors.seen` and tells the person through `systemMessage`, since plain SessionStart stdout reaches only the model. A launcher with no build prints its fixed JSON line itself.
- *Met* (`hooks.rs`, module doc). Two places write no log by design: input failures outside a git repository, where logging would create a state dir in the user's folder (field guide HK-10), and Cowork, where hooks write nothing to disk. Since step 6b both say so in the hook's output instead (CLI-09). The report reads at most the log's last 256 KiB, counting "at least <n>" past it. Between sessions, `weighin status --json` (CLI-12, step 6d) says the same without a session start: `hook_errors` counts the lines the next SessionStart will report, and `health` is `degraded` while there are any (`hooks/errors`). It reads the log and the seen record only, so the session start still reports them. Since step 6f the mod's band reads it at each refresh and adds the warning count ("· <n> warning(s): /wi status").

**HK-4. A guard is linear-time by construction.** A PreToolUse hook that times out lets the call through, so a slow match is a bypass. A guard matches in linear time (no backtracking), caps its input, and carries a timing test at the cap.
- *Not applicable today* (no guard). PostToolUse is not a guard: a timeout there loses a capture or a recall line, never lets something through.

**HK-5. Budget time inside the hook.** Each hook plans against its own `hooks.json` timeout and measures as it goes; sub-steps get explicit slices.
- *Met* (heartbeat in step 6c) for the two hooks that do bounded network or store work: Stop's journal export, `Budget::STOP` (18 s worst case in its 20 s timeout), and SessionStart's import, `Budget::SESSION_START` (8 s in 10 s, store wait included); `hooks_json_timeouts_match_the_budgets` pins both timeouts. The store wait in every hook is `Wait::Hook` (2 s). The heartbeat (step 6c, decision D8) lets the next hook tell a timeout from an interruption: a hook of a registered event keeps `hook-heartbeat-<Event>` in `<git-common-dir>/redkiln/weighin/` (`running`, a beat every second from one scoped, named thread that ends with the hook, then `finished`), only in git, never in Cowork, and only where that `redkiln/` exists already; slots are regular files only (HK-6). Every such hook reads the four slots before its dispatch: a `running` slot past its deadline is dead whatever its beat's age, `timed-out` when its last beat came within 3 s of the deadline, else `interrupted`, and one before its deadline is dead, `interrupted`, once its beat is more than 5 s old (6c review F1 and round 2); the hook logs one line under the dead hook's event, which the next SessionStart reports with the other hook errors (CLI-09's note rules apply to a line it cannot log), and rewrites the slot so it is logged once. The timeouts per event are the adapter's (`claude_code::timeout`), pinned against `hooks.json` (`the_timeouts_match_hooks_json`). `weighin status` (step 6d) reads the four slots without writing (`heartbeat::slots`), reports each event's state as the next hook would judge it, with its last beat as `at`, and a death no hook has logged yet as the warning `hooks/lost:<Event>`. *Residuals:* times are whole seconds and `started` is floored and read after the harness's timer starts, so a hook its timeout killed less than about a second before the next hook of its event starts, or one interrupted less than 5 s before, is overwritten unseen; two hooks finding the same dead slot may both log it; two `PostToolUse` hooks share a slot, so one finishing can hide the other's death for about a second; a lost line logged before the hook's own first failure makes the log hold an unreported line, so that failure is counted at the next session start rather than noted (D2 B); a heavily starved beater could make a live hook look interrupted after 5 s.

**HK-6. Cap stdin, read only the fields used, every field optional.** Caps are per event; a payload field is read as optional and unknown fields are ignored, so a new Claude Code field never breaks a hook; hook state files are read only when they are regular files.
- *Met* (step 6b): fields are read by name from the payload, each with a fallback, and unknown fields are ignored. The adapter reads at most SessionStart 64 KiB, Stop and SubagentStop 4 MiB, anything else 8 MiB, by the event on the command line (decision D9); a payload over its cap dispatches nothing, is logged inside git and noted (CLI-09). `hook-errors.log`, `hook-errors.seen`, the journal watermark and the Windows shell copy are read, appended or overwritten only when `symlink_metadata` says they are regular files or absent, and the state dir must be a directory, not a link (`src/state_file.rs`). *Residual:* the check and the open are two calls, so a symlink swapped in between is followed; closing that needs `O_NOFOLLOW`, which std does not offer without `libc`, a new dependency (H-16) not asked for.

**HK-7. The Stop gate has honest exits and a loop breaker.** A Stop hook that can block runs only when the turn changed what it gates, stands down on a final `Status: WIP` or `Status: BLOCKED`, names that exit in every block message, and breaks a repeated block of the same tree for the same reason.
- *Met by never blocking:* Weigh-In's Stop and SubagentStop hooks never block and never stop the session (no `decision` or `continue` in any response; pinned by the test under CLI-09), so they spend none of the shared Stop budget. Stop's export spends only its own time, within `Budget::STOP`, without waiting on a sibling hook. A nudge about a one-way question is a `systemMessage`, never a block, and never starts a sitting.

**HK-8. Deny messages name the sanctioned route.** A refusal says what to do instead and that a retry will be refused again.
- *Not applicable today* (no deny). Weigh-In's warnings follow its spirit: each names what to fix or run (the store path, the config file, `/weigh-in`).
