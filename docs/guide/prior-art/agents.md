# Prior art for redkiln's agent practices (2024-2026)

How redkiln's eight working approaches compare with published practice. Each bullet says whether we **agree**, should **adopt** something, or **differ**, and gives its source. Every source below was opened or appeared in search results on 2026-11-01. Where a claim rests on a secondary summary rather than the primary page, the bullet says so.

## 1. Hooks: fail open, guards fail closed, Stop gate with a fresh reviewer

- **Exit 2 blocks; exit 1 only warns.** Claude Code treats exit 2 as the blocking signal: "Exit 2 blocks even when your hook prints JSON," and "If your hook is meant to enforce a policy, use `exit 2`." Exit 1 without valid JSON is a non-blocking error. *Agree*: our guards must exit 2 (or deny through `permissionDecision`). The launcher must never turn a guard's refusal into exit 1. Source: [Hooks reference](https://code.claude.com/docs/en/hooks)
- **Hooks fail open by default; `onFailure: "block"` makes a guard fail closed.** By default, a missing script or a crash lets the action proceed. A timed-out PreToolUse hook does not block unless `onFailure: "block"` is set (v2.1.295+). *Agree, and adopt*: this matches "hooks fail open, guards fail closed" exactly. Guards should declare `onFailure: "block"` in `hooks.json`, so a crash or timeout inside a guard also blocks, not only a refusal the binary returns. The binary's own `--fail-closed` handling should stay as well. Source: [Hooks reference](https://code.claude.com/docs/en/hooks)
- **Silence is not approval.** "The hook can deny the call, but staying silent doesn't approve it." A PreToolUse decision can be `allow`, `deny`, `ask` or `defer`. *Agree*: guards should only ever deny or stay silent, never `allow`, so they cannot widen the user's permission rules. `ask` is worth using for one-way-door edits: it lets the human approve in place where a guard would otherwise refuse. Source: [Hooks reference](https://code.claude.com/docs/en/hooks)
- **Stop hooks have a block cap.** If a Stop hook blocks eight stops in a row with no tool call in between, Claude Code overrides the next block and ends the turn (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`). The SubagentStop input carries `stop_hook_active`. *Adopt*: our Stop gate should expect the cap. When the harness forces the turn to end after repeated refusals, the gate should record that as an unhonest end (a ledger event), so the next SessionStart surfaces it. As things stand, a forced end is silent. Source: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- **Hooks for zero-exception rules only.** "If something has to happen every time, make it a hook ... `CLAUDE.md` is for guidelines." Anthropic warns: "keep the enforced set small. ... If you ever find yourself at forty of them, most are probably preferences." *Agree, with a caution*: temper's guard surface is large. Each guard should map to an H-rule with zero exceptions, and anything that is a preference should move to the skill. Source: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- **`prompt` and `agent` hooks are not deterministic.** Anthropic: "A `prompt` or `agent` hook asks *another model* to decide, so it isn't deterministic either. For real enforcement, use a `command` or `http` hook." *Agree*: we keep the reviewer verdict out of hook code and route it through the binary as a recorded, validated artifact. That is stronger than the built-in `agent` hook. Source: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- **The fresh-context reviewer is now the documented pattern.** `/code-review` "reviews the diff in a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code." The page also warns: "A reviewer that's asked to find problems will always find *something*", so it advises adding "skip style". *Agree; adopt the scope limit*: the rust-reviewer brief should tell the reviewer to report only correctness and rubric violations, so its approval does not loop on nitpicks. Source: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- **Lint on every edit, with the edit rejected.** SWE-agent's ablation found that "the dedicated edit action with linting is the most critical component": an edit that fails the linter is refused before it lands. Aider runs `--lint-cmd` after each edit and `--test-cmd` with `--auto-test`, and "will try and fix any errors if the command returns a non-zero exit code." *Agree*: this is our PreToolUse refusal plus Stop gate. *Adopt* SWE-agent's lesson that refusing at edit time beats discovering at stop time, for cheap checks such as a syntax check. Sources: [SWE-agent (arXiv 2405.15793)](https://arxiv.org/abs/2405.15793v2), [Aider: linting and testing](https://aider.chat/docs/usage/lint-test.html)
- **Agents game tests, so tests need a guard.** ImpossibleBench mutates tests until they contradict the spec, then measures how often agents "pass" anyway. Hiding tests cut cheating to near zero but hurt legitimate performance; read-only test access was the middle ground. *Agree*: H-12's guard against weakening tests is well founded. *Adopt*: guards could make existing test files read-only during the green step, not only scan the diff for weakened assertions. Source: [ImpossibleBench (arXiv 2510.20270)](https://arxiv.org/abs/2510.20270v1)
- **Hooks are not a sandbox.** Codex pairs approval policy with an OS sandbox: `workspace-write` turns network off by default and keeps `.git` read-only even inside writable roots. Claude Code's docs say `if` filtering is best-effort: "use the permission system rather than a hook to enforce a hard allow or deny." *We differ, deliberately*: our guards are a quality layer, not a security boundary. Docs should say so, and unattended lanes should also run under a sandbox and deny rules. Sources: [Codex sandbox](https://developers.openai.com/codex/sandbox), [Hooks reference](https://code.claude.com/docs/en/hooks)

## 2. LLM judgement does not drive control flow until it is scored

- **Binary pass/fail judges, calibrated to one principal expert.** Hamel Husain calls 1-5 scales "doing it wrong." His method has one principal domain expert give pass/fail with a written critique, and the critiques become few-shot examples. The judge is treated as a classifier with train/dev/test splits and a hidden test set. He warns that raw agreement "can be misleading when failures are rare." *Agree*: our labelled corpus and binary detected/missed outcomes match. *Adopt*: report true-positive and true-negative rates separately, never raw agreement, and keep a held-out test split that prompt iteration never sees. Source: [Using LLM-as-a-Judge (Hamel Husain)](https://hamel.dev/blog/posts/llm-judge/)
- **Measure judges with classification metrics and Cohen's kappa.** Eugene Yan recommends binary outputs "where possible," precision and recall for binary judgments, and Cohen's κ because it corrects for chance. He is skeptical of correlation metrics that "look overly optimistic." *Adopt*: add κ against the owner's labels to the replay gate's report, beside the noise-rate margin. Source: [Evaluating the Effectiveness of LLM-Evaluators (Eugene Yan)](https://eugeneyan.com/writing/llm-evaluators/)
- **Known judge biases: position, verbosity, self-preference.** MT-Bench found that all judges showed position bias and were prone to verbosity bias, while strong judges still reached over 80% agreement with humans. Panickssery et al. show that evaluators recognise and favour their own generations, and that self-recognition correlates linearly with self-preference. *Adopt*: the reviewer that judges a diff should not share a model and prompt lineage with the implementer where we can avoid it. Pairwise comparisons in calibration should be run in both orders. Sources: [Judging LLM-as-a-Judge (arXiv 2306.05685)](https://arxiv.org/abs/2306.05685v1), [LLM Evaluators Recognize and Favor Their Own Generations (arXiv 2404.13076)](https://arxiv.org/abs/2404.13076v1)
- **Expert-domain agreement can be low.** In dietetics and mental health, LLM judges agreed with subject experts only 60-64% of the time, against 72-75% between experts. Expert personas helped by only about 4%. *Agree*: this is exactly why our verdicts stay advisory until scored. Source: [Limitations of LLM-as-a-Judge in expert knowledge tasks (arXiv 2410.20266)](https://arxiv.org/pdf/2410.20266)
- **Criteria drift.** Shankar et al. found that "it is impossible to completely determine evaluation criteria prior to human judging of LLM outputs," and that a model swap can cause drift. *Adopt*: re-run the corpus replay gate when the model changes, not only on prompt or rubric edits. Let the owner's labelling sessions amend the rubric, versioned like the prompts. Source: [Who Validates the Validators? (arXiv 2404.12272)](https://arxiv.org/pdf/2404.12272)
- **Multiple trials; pass@k versus pass^k; graduation into regression suites.** Anthropic: "model outputs vary between runs." Use pass^k when consistency matters. Separate capability evals (a "hill to climb") from regression evals that sit near 100%. Give model graders an "Unknown" option and grade each rubric dimension separately. Start with "20-50 simple tasks drawn from real failures." *Agree*: k=3 with no detected-to-missed flips is a pass^k regression rule. *Adopt*: an explicit "Unknown" verdict for the reviewer, per-dimension grading, and capability cases kept apart from the regression corpus. Source: [Demystifying evals for AI agents (Anthropic)](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)
- **Grade outcomes, not paths, and read transcripts.** The same post says it is "often better to grade what the agent produced, not the path it took." Reading transcripts tells an agent's mistake apart from a grader wrongly rejecting a valid solution. *Agree*: the corpus labels findings, not reasoning traces. *Adopt*: add transcript review to the replay gate's report whenever a case flips. Source: [Demystifying evals for AI agents (Anthropic)](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)
- **Small samples first, plus human testing.** Anthropic's research system found that about 20 real queries revealed large effects, and that a single judge prompt giving a 0.0-1.0 score and a pass/fail matched humans best. Human testers still caught failures that automation missed. *Agree*: promotion stays a human config edit. Source: [How we built our multi-agent research system (Anthropic)](https://www.anthropic.com/engineering/built-multi-agent-research-system)
- **The evaluator-optimizer loop needs clear criteria.** Anthropic's pattern pairs a generator with an evaluator in a loop. It works best with "clear evaluation criteria" and when feedback measurably improves results. *Agree*: our implement-then-review loop is this pattern, and the scored rubric is what makes its criteria clear. Source: [Building effective agents (Anthropic)](https://www.anthropic.com/engineering/building-effective-agents)

## 3. Headless `claude -p`, stream-json, supervision, cost, capacity

- **`--bare` for reproducible headless runs.** Bare mode skips the auto-discovery of hooks, skills, plugins, MCP servers, auto memory and CLAUDE.md. It is "the recommended mode for scripted and SDK calls, and will become the default for `-p`." Without it, `-p` runs a project's hooks and `.mcp.json` "even in a folder you've never trusted." *Adopt*: every supervised `claude -p` (assay review, loop lanes) should pass `--bare` and inject exactly the settings, agents and plugin it needs (`--settings`, `--agents`, `--plugin-dir`). This closes the gap where a reviewed PR's own `.claude/settings.json` can run hooks. Source: [Run Claude Code programmatically](https://code.claude.com/docs/en/headless)
- **The stream-json contract to parse.** The last line is a `result` message carrying cost and session metadata. `system/init` reports `plugins`, `plugin_errors`, `mcp_servers` and `mcp_server_errors`, so CI can fail when a plugin did not load. `system/api_retry` events carry `attempt`, `error_status` and a closed `error` category. Subagent messages carry `parent_tool_use_id`. *Adopt*: fail the run on a non-empty `plugin_errors`. Feature-detect through the `capabilities` array rather than comparing version strings. Map `api_retry.error` into the infra-failure class. Source: [Run Claude Code programmatically](https://code.claude.com/docs/en/headless)
- **Signals and exit codes.** SIGTERM exits 143 and "records no result" for the turn in progress. To end the turn cleanly, "send SIGINT ... before you stop the process." `--permission-prompts none` turns would-be prompts into `permission_denials` in the result. *Adopt*: the supervisor should send SIGINT, wait, then SIGTERM, and treat exit 143 as cancelled, not failed. Pass `--permission-prompts none` so an unattended lane can never hang on a prompt. Source: [Run Claude Code programmatically](https://code.claude.com/docs/en/headless)
- **Cost accounting rules.** `total_cost_usd` in the result message is authoritative, though it is a "client-side estimate." Usage within a turn must be deduplicated by message ID (take the highest `output_tokens` when two disagree). With `--resume`, the reported total includes earlier runs. *Agree*: our cost accounting takes the result total. *Adopt*: the resume rule. Store the delta from the previous result, not the reported total, or the capacity ledger will double-count resumed sessions. Source: [Agent SDK cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)
- **Structured output instead of prose parsing.** `--json-schema` with `--output-format json` returns a `structured_output` field, which is absent when the run ends without valid output. *Adopt*: reviewer runs should emit findings through `--json-schema` (we already validate contract schemas), and treat a missing `structured_output` as a run failure. Source: [Run Claude Code programmatically](https://code.claude.com/docs/en/headless)
- **Recovery and deployment of long-running agents.** Anthropic built systems that "resume from where the agent was when the errors occurred," and uses "rainbow deployments" so agents mid-task keep their old version while traffic shifts. *Agree*: leases plus resumable runs match. *Adopt*: pin a lane to the plugin and binary version it started with until it finishes, like a rainbow deployment, rather than letting a release change the rules mid-lane. Source: [How we built our multi-agent research system (Anthropic)](https://www.anthropic.com/engineering/built-multi-agent-research-system)

## 4. Prompt-injection defence for AI PR review

- **The lethal trifecta.** Private data, untrusted content and external communication together make an agent exploitable. Willison: guardrails that catch "95% is very much a failing grade." His example is a GitHub MCP tool that read public issues, could access private repositories, and could open PRs. *Agree*: assay's reviewer reads untrusted PRs. We remove the exfiltration leg (no network, sanitised output, publication by deterministic code) rather than trust detection. Source: [The lethal trifecta (Simon Willison)](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- **Constrain the agent once it has read untrusted input.** Design-pattern paper: once an agent has taken in untrusted input, "it must be constrained so that it is impossible for that input to trigger any consequential actions." The paper's patterns include Action-Selector, Plan-Then-Execute, LLM Map-Reduce, Dual LLM, Code-Then-Execute and Context-Minimization (pattern list from secondary summaries). *Agree*: assay's reviewer only emits a document that deterministic code validates and publishes, which is Plan-Then-Execute or Dual LLM in shape. *Adopt*: name the pattern in the threat model and use Map-Reduce, one isolated reviewer per shard, for large diffs. Source: [Design Patterns for Securing LLM Agents against Prompt Injections (arXiv 2506.08837)](https://arxiv.org/abs/2506.08837)
- **CaMeL: control flow from the trusted query only.** CaMeL extracts control and data flow from the trusted query, so untrusted data "cannot affect the program flow," and enforces capability policies on tool calls. It reached 77% task success with provable security, against 84% undefended. *Agree in spirit*: our "LLM output never drives control flow until scored" rule is a CaMeL-like split. *We differ*: we do not taint-track individual values. A cheap step toward it is to tag every published string with its provenance (model or publisher) and let the sanitiser key on the tag. Source: [Defeating Prompt Injections by Design (arXiv 2503.18813)](https://arxiv.org/abs/2503.18813)
- **OWASP LLM01 mitigations match our list.** The seven strategies are: constrain behaviour, define and validate output formats with deterministic code, filter input and output, least privilege, human approval for high-risk actions, "Separate and clearly denote untrusted content," and adversarial testing. *Agree* on all but the last. *Adopt*: an injection suite in the corpus (`corpus/inject/**` exists). Run it in the replay gate as a must-not-regress set. Source: [OWASP LLM01:2025 Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)
- **Excessive agency.** OWASP LLM06 traces excessive agency to excessive functionality, permissions and autonomy. The fixes: minimal extensions, least privilege, human approval for high-impact actions, authorisation enforced downstream, and logging. *Agree*: the dedicated GitHub App, the token per job and the verdict check are downstream authorisation. Source: [OWASP LLM06:2025 Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
- **Pwn requests and the two-workflow split.** GitHub Security Lab: `pull_request_target` with an explicit PR checkout is "a dangerous practice." Build untrusted code in `pull_request`, pass results as artifacts to a privileged `workflow_run`, and remember that "Artifacts resulting from untrusted PR data are themselves untrusted." Label gating "is still prone to a race condition." Use `persist-credentials: false`. *Agree*: assay authenticates artifacts by digest and reads config from the base branch. *Adopt*: an explicit test that no privileged job sets `persist-credentials: true`. Treat label-triggered paths as racy unless they are bound to a head SHA (assay's decide-only already binds `head_sha`). Source: [Preventing pwn requests (GitHub Security Lab)](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests)
- **GitHub will enforce a `pull_request_target` policy.** The docs say the default policy blocks `pull_request_target` in public repositories, "On December 2, 2026, GitHub will enforce the default policy." They also say to populate caches only from trusted triggers, use ephemeral runners, and note that `allow-unsafe-pr-checkout` does not cover `git fetch` or downloaded artifacts. *Adopt*: check whether assay's decide-only workflow uses `pull_request_target`, and settle the policy before that date. Source: [Securely using pull_request_target (GitHub Docs)](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)
- **Comment-and-Control: PR metadata interpolated into prompts.** Researchers made Claude Code's security-review action, Gemini CLI's action and Copilot's agent leak credentials. In the Claude case, the PR title was interpolated into the prompt "with zero sanitization." Anthropic's docs say the action should only review trusted PRs (secondary coverage). *Agree*: this is why our prompts never interpolate PR text into instructions. *Adopt*: a regression case with a hostile title, branch name and commit message. Source: [SecurityWeek on prompt injection via GitHub comments](https://www.securityweek.com/claude-code-gemini-cli-github-copilot-agents-vulnerable-to-prompt-injection-via-comments/)
- **Copilot coding agent's controls.** Hidden characters such as HTML comments are filtered out before the agent sees them. The agent pushes only to one `copilot/` branch. Workflows need "Approve and run workflows." There is a firewall. Only users with write access can trigger the agent, and comments from users without write access are never shown to it. Commits are co-authored by the requester. *Adopt*: strip HTML comments and invisible Unicode from PR bodies and comments before they reach a reviewer prompt, and drop non-writer comments from the reviewer's context entirely. Our sanitiser works on output, not input. Source: [Risks and mitigations for GitHub Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)
- **MCP: no token passthrough.** "MCP servers must not accept tokens that were not explicitly issued to them." Passthrough also breaks rate limiting and audit logging. *Agree*: forge takes minted, scoped tokens per job. This becomes relevant if any rk plugin ships an MCP server. Source: [MCP security best practices](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices)

## 5. Human in the loop: decision ledger, door types, approvals bound to a hash

- **Type 1 and Type 2 decisions.** Bezos's 2015 letter splits decisions into consequential, irreversible Type 1 and reversible Type 2. The failure mode is applying "the heavy-weight Type 1 decision-making process on most decisions," which leads to slowness and too little experimentation (quoted via secondary sources; the letter itself was not opened). *Agree*: "decide two-way calls, block on one-way ones" is this. *Adopt*: track the ratio. If most ledger items are one-way, the classification is too heavy. Sources: [Reversible and irreversible decisions (Farnam Street)](https://fs.blog/reversible-irreversible-decisions/), [One-way and two-way doors (Charlie Kindel)](https://blog.kindel.com/2019/06/27/one-way-and-two-way-doors/)
- **Nygard ADRs: never delete, supersede.** The five sections are Title, Context, Decision, Status and Consequences. A reversed decision stays and is marked superseded, because it "was once the decision." *Agree*: our decision logs say "what they supersede." *Adopt*: Nygard's Consequences section, positive, negative and neutral, which our one-line log rows usually omit. Put it in the knowledge atom. Source: [Documenting Architecture Decisions (Michael Nygard)](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
- **MADR: considered options.** MADR adds "Considered Options," with numbered `docs/adr/NNNN-title.md` files. Log4brains-style variants add draft status and tags. *Adopt*: decision atoms should keep the rejected options (assay's log does this in prose: "Rejected: ..."). Ledger cards already carry options, so persist them in the atom. Sources: [MADR repository](https://github.com/sdiachen/madr), [JabRef ADR-0000: use MADR](https://jabref.readthedocs.io/en/latest/adr/0000-use-markdown-architectural-decision-records/)
- **Interrupt-and-resume with a checkpointer.** LangGraph's `interrupt()` saves graph state and pauses "indefinitely ... until you resume." The human can approve, edit or reject a tool call, and the pause requires a checkpointer. *Agree*: the ledger is our checkpointer for human decisions. *We differ*: ours is asynchronous (the session keeps doing independent work), which suits AFK runs better than a blocking interrupt. Source: [LangGraph human-in-the-loop](https://docs.langchain.com/oss/python/langgraph/human-in-the-loop)
- **Approvals must go stale when content changes.** GitHub models this as `dismiss_stale_reviews_on_push` and `require_last_push_approval` (the last push approved by someone other than its pusher). Datadog flags disabling either, since a previously approved PR could merge unreviewed. *Agree, and we are ahead*: binding an approval to a content hash is stricter than GitHub's push-based staleness, because a rebase that changes nothing does not invalidate it while any real change does. Sources: [GitHub ruleset pull-request parameters (OpenAPI bindings)](https://docs.rs/crate/openapi-github/latest/source/docs/RepositoryRulePullRequestParameters.md), [Datadog rule: review settings altered](https://docs.datadoghq.com/security/default_rules/def-000-a0l/)
- **The requester cannot be the approver.** In Copilot's cloud agent, the user who asked for a PR cannot approve it, and the agent cannot mark it ready, approve or merge. *Adopt*: an approval that wi-880b66 lets an agent merge on should be rejected when the reviewer subagent was spawned by the same session that wrote the code, unless it ran with fresh context and a different brief. Record the spawner in the approval record. Source: [Risks and mitigations for GitHub Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)

## 6. Agent instructions: AGENTS.md charters, CLAUDE.md imports, skills, context budgets

- **Claude Code now reads AGENTS.md natively, with one catch.** Since v2.1.277, Claude Code reads AGENTS.md, but "only when you have no `CLAUDE.md` in your working directory or above it." A CLAUDE.md that imports AGENTS.md is the documented way to share the file. Imports recurse at most "four hops." *Agree*: our `CLAUDE.md` containing `@AGENTS.md` is the recommended shape. Keep it, because a CLAUDE.local.md would otherwise silently stop AGENTS.md from loading. Source: [How Claude remembers your project](https://code.claude.com/docs/en/memory)
- **Size budget and path-scoped rules.** Target "under 200 lines per CLAUDE.md file." Imports "don't reduce its context cost." Use `.claude/rules/` with `paths:` frontmatter for rules that matter only in part of the tree. *Adopt*: redkiln's and assay's root charters, especially assay's long decisions log, far exceed 200 lines and load on every session. Move the decision log out of AGENTS.md into `docs/decisions/` or `.kb`, and keep a pointer. Source: [How Claude remembers your project](https://code.claude.com/docs/en/memory)
- **Codex concatenates root-to-leaf with a 32 KiB cap.** Codex reads one file per directory from the git root down to the cwd (`AGENTS.override.md`, then `AGENTS.md`). It joins them root-first, so deeper files win, and stops at `project_doc_max_bytes`, 32 KiB by default. *Adopt for harness-agnosticism*: keep root plus crate charters under 32 KiB combined, or Codex will silently truncate the crate charter, which is the part that matters most. Add a CI size check. Source: [Codex AGENTS.md guide](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- **AGENTS.md is a neutral standard.** OpenAI donated AGENTS.md to the Agentic AI Foundation under the Linux Foundation, co-founded with Anthropic and Block. *Agree*: per-crate AGENTS.md charters are the portable choice. Source: [Agentic AI Foundation (OpenAI)](https://openai.com/blog/agentic-ai-foundation)
- **Other harnesses scope rules to paths.** Cursor has Always, Auto Attached (glob), Agent Requested (description) and Manual rules in `.cursor/rules`. Copilot uses `.github/instructions/*.instructions.md` with `applyTo` globs and `excludeAgent`, and its CLI reads AGENTS.md. *Agree*: path-scoping is consensus. Our per-crate AGENTS.md is the portable form of it. Sources: [Cursor project rules](https://docs.cursor.com/context/rules), [Adding repository custom instructions for Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions)
- **The Agent Skills spec's progressive disclosure budget.** Metadata is about 100 tokens. The SKILL.md body should stay under 5,000 tokens and 500 lines, and references should go "one level deep." `name` is at most 64 characters and must match the directory; `description` is at most 1,024 characters. Validate with `skills-ref validate`. *Adopt*: run `skills-ref validate` in the plugins CI job. Check the rust-craft skill's body against the 5k-token and 500-line budget, since `rules.md`, with 182 rules, belongs in `references/`. Source: [Agent Skills specification](https://agentskills.io/specification)
- **Claude Code's skill listing truncation and portability limits.** The `description` and `when_to_use` text are truncated "at 1,536 characters in the skill listing." A loaded skill "stays in context across turns." Outside Claude Code (claude.ai uploads, the Skills API), only six fields are allowed (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`), and any other key "cause[s] a hard error." *Adopt*: lint rk-* skills for claude.ai-safe frontmatter, since we ship to claude.ai. Put the key use case first in every description. Source: [Claude Code skills](https://code.claude.com/docs/en/skills)
- **Smallest high-signal context.** Anthropic frames context engineering as finding the smallest set of high-signal tokens. Its long-horizon techniques are compaction, structured note-taking and sub-agents (summary from the search result). *Agree*: SessionStart context budgets apply this. Note that SessionStart `additionalContext` is capped at 10,000 characters, should be written "as factual statements," and runs again on resume. Sources: [Effective context engineering for AI agents (Anthropic)](https://anthropic.com/engineering/effective-context-engineering-for-ai-agents), [Hooks reference](https://code.claude.com/docs/en/hooks)
- **Write down only what the agent cannot discover.** "Claude already knows most of what you might be tempted to write down." Keep commands, non-repo decisions and environment facts. "If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook." *Agree*: our charters repeat the H-rules that temper enforces anyway. *Adopt*: shorten that block to a pointer, since the guard enforces it and the skill teaches it. Source: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- **Devin keeps Knowledge and Playbooks apart.** General practices live in Knowledge. Playbooks are reusable prompts for recurring tasks, and Devin can derive them from successful sessions. *Agree*: this is the same split as .kb atoms versus skills. Source: [Devin: creating playbooks](https://docs.devin.ai/product-guides/creating-playbooks.md)

## 7. Autonomous SDLC loop: plan, test-first, review, gate; worktrees; recovery; replay

- **Long-running harness: initializer, JSON feature list, progress file, git.** Anthropic's harness uses a one-time initializer that writes an init script, a progress log and an initial commit. Features live in JSON with `"passes": false`, and agents "may only update the passes field." JSON is used because models are less likely to overwrite it. Agents work on "only one feature at a time." Each session starts by reading the git log and the progress file and running an end-to-end check. The named failure modes include declaring victory early. *Agree*: the plan-test-gate loop and the honest WIP status target the same failures. *Adopt*: keep machine-owned plan state in JSON with a single writable field per item, and run a start-of-lane smoke check before new work. Source: [Effective harnesses for long-running agents (Anthropic)](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- **Event-sourced state with deterministic replay.** The OpenHands SDK uses an immutable configuration and an append-only event log as the source of truth, with stateless agents, local-to-remote portability and sandboxed execution. It reports "negligible event-sourcing overhead." *Agree*: this validates our happenstance event-ledger design. *Adopt*: their split of immutable agent configuration from the event log. Record the exact prompt bundle hash and model in the lane's first event, as assay's evidence key already does. Source: [The OpenHands Software Agent SDK (arXiv 2511.03690)](https://arxiv.org/abs/2511.03690)
- **Worktrees for parallel lanes.** Claude Code documents `--worktree`, subagent `isolation: worktree`, `.worktreeinclude` and cleanup. Nested CLAUDE.md files inside `.claude/worktrees/` have their own loading rules. *Agree*: lanes in worktrees are the documented pattern. *Adopt*: use `.worktreeinclude` for the files a lane needs that git ignores, such as `.claude/` local state, instead of copying them by hand. Sources: [Run parallel sessions with worktrees](https://code.claude.com/docs/en/worktrees.md), [How Claude remembers your project](https://code.claude.com/docs/en/memory)
- **Ask for evidence, not claims.** "'All tests pass' on its own tells you very little." Ask for the command and its output. For unattended sessions, "it's also the only evidence you have." *Agree*: our Status block names the gate result. *Adopt*: the Stop gate should store the gate's own output digest in the ledger, so a reported status can be checked against the recorded run. Source: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- **Stopping conditions and sandboxed testing.** Anthropic recommends stopping conditions such as maximum iterations, "extensive testing in sandboxed environments," and poka-yoke tool design, for example requiring absolute paths, which removed relative-path errors. *Agree*: leases, budgets and attempt caps are our stopping conditions. *Adopt*: poka-yoke in our CLIs (absolute paths only, closed enums), which assay already practises. Source: [Building effective agents (Anthropic)](https://www.anthropic.com/engineering/building-effective-agents)
- **Benchmarks are noisy; verify the tests themselves.** SWE-bench Verified exists because many tasks were underspecified or had tests that rejected correct fixes. Each sample was labelled three times and the worst label kept, leaving 500 of 1,699. *Adopt*: label corpus cases by more than one pass, keeping the highest severity, and drop cases whose expected finding is disputed rather than letting them inflate the miss rate. Source: [Introducing SWE-bench Verified (OpenAI)](https://openai.com/index/introducing-swe-bench-verified/)
- **The agent never merges its own work.** In Copilot's cloud agent, drafts must be reviewed and merged by a human, and the agent cannot approve or merge. *We differ, deliberately*: wi-880b66 lets agents merge under a strict bar. The prior art suggests keeping that bar tighter than human merges: a fresh-context approval cited on the PR, never a self-approval, and never release or one-way-door PRs. Source: [Risks and mitigations for GitHub Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)

## 8. Harness-agnostic: CLI first, thin plugin layer

- **Agent Skills is an open, cross-platform standard.** Anthropic published Agent Skills as "an open standard for cross-platform portability," and skills run across Claude.ai, Claude Code, the Agent SDK and the API. *Agree*: our skills are the portable layer. Keep harness-specific frontmatter optional, per section 6. Sources: [Equipping agents for the real world with Agent Skills (Anthropic)](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills), [agentskills.io](https://agentskills.io/)
- **Agent Client Protocol.** ACP is Zed's Apache-licensed protocol: the editor launches the agent as a subprocess and they talk JSON-RPC 2.0 over stdio, "LSP for agents." Gemini CLI, and reportedly Claude, Codex and others, plug in. *Consider*: if rk-loop ever drives harnesses other than Claude Code, ACP is the emerging neutral way to drive one. Our `--json` CLIs sit below it and stay valid. Source: [Agent Client Protocol (Zed)](https://zed.dev/acp)
- **Hooks are the non-portable layer.** Codex expresses safety as sandbox and approval policy rather than hook scripts. Claude Code's hooks are rich but specific to Claude Code. *Agree*: keeping all policy in the CLI, with the hook only a JSON adapter, is the right separation. *Adopt*: one adapter per harness, each a thin translation of the same `anneal`/`temper` verdict, plus a conformance fixture set per adapter. Sources: [Codex sandbox](https://developers.openai.com/codex/sandbox), [Hooks reference](https://code.claude.com/docs/en/hooks)
- **Avoid frameworks that hide prompts.** Anthropic: frameworks "can add abstraction layers that hide prompts and responses, making debugging harder." Start with the APIs directly. *Agree*: our direct `claude -p` supervision with recorded prompt bundles follows this. Source: [Building effective agents (Anthropic)](https://www.anthropic.com/engineering/building-effective-agents)
- **Model-agnostic routing as a design goal.** The OpenHands SDK lists model-agnostic multi-LLM routing and local-to-remote portability as features. *Consider*: a model-agnostic runner port (assay already has `ModelRunner`) is what makes a second reviewer model, against self-preference bias (section 2), cheap to add. Source: [The OpenHands Software Agent SDK (arXiv 2511.03690)](https://arxiv.org/abs/2511.03690)
