# Prior art for redkiln's platform choices

Each bullet is marked **agree** (prior art matches what we do), **adopt** (prior art does something better that we should take), or **we differ** (we depart from it on purpose, with the reason). Research done on 2026-11-01. Every link was opened or appeared in search results during this research.

## 1. Event store (SQLite, append-only, TRUNCATE journal, projections)

- **WAL needs one host and shared memory.** SQLite's WAL page lists as its first disadvantage that "WAL does not work over a network filesystem", because the wal-index needs shared memory. It also warns that separating the database from its `-wal` file can lose committed transactions or corrupt the database. **Agree:** this is our reason for not using WAL in cloud-synced or Cowork folders, where a sync client may move or drop side files. Source: [Write-Ahead Logging](https://www.sqlite.org/wal.html)
- **TRUNCATE avoids directory changes, and PERSIST is the next step down.** The pragma docs say TRUNCATE commits by truncating the journal "instead of deleting it", so "the containing directory does not need to be changed". PERSIST zeroes the journal header and never deletes or truncates at all. **Agree:** TRUNCATE fits folders that refuse deletes. **Adopt:** keep PERSIST as a documented fallback for filesystems where truncation is also refused or slow. Source: [PRAGMA statements](https://www.sqlite.org/pragma.html)
- **Stamp `application_id` as well as `user_version`.** `user_version` (header offset 60) is free for the application to use. `application_id` (offset 68) lets `file(1)` and tools identify the file type. **Adopt:** set an `application_id` for `events.sqlite3`, so a stray copy can be recognised and our own opener can refuse a SQLite file that is not ours. Source: [PRAGMA statements](https://www.sqlite.org/pragma.html)
- **Never close a database file descriptor that SQLite has open, and link only one copy of SQLite.** "How to corrupt" explains that POSIX advisory locks are dropped when *any* descriptor on the file is closed, including one opened to sniff the header or make a backup. It also describes a shipped product corrupted by two linked SQLite copies. **Adopt:** add a rule and a test that nothing outside happenstance opens `events.sqlite3` directly; use `VACUUM INTO` or the backup API for copies. Watch for two `libsqlite3-sys` builds in the dependency tree. Source: [How To Corrupt An SQLite Database File](https://www.sqlite.org/howtocorrupt.html)
- **Hot journals must travel with the database.** Deleting or renaming a hot `-journal` after a crash prevents recovery, and copying a live database file is unsafe. **Agree:** this supports exporting through JSONL journals rather than copying the `.sqlite3` file between containers. Source: [How To Corrupt An SQLite Database File](https://www.sqlite.org/howtocorrupt.html)
- **Shared files over a network are discouraged.** SQLite's "Appropriate uses" checklist says to choose client/server when data is "separated from the application by a network", because "file locking logic is buggy in many network filesystem implementations". **We differ, deliberately:** each ledger has one local writer per machine and syncs by export/import, not by concurrent access. Document that two machines must never open the same synced file at once. Source: [Appropriate Uses For SQLite](https://sqlite.org/whentouse.html)
- **Writers should use `BEGIN IMMEDIATE`.** A DEFERRED transaction that reads first and then writes "will fail with SQLITE_BUSY" if another connection is writing, and the busy timeout does not help at that point. COMMIT can also return BUSY. **Adopt:** make every write path on hook hot paths take `BEGIN IMMEDIATE` (or check that happenstance does), so the bounded busy timeout actually applies. Source: [Transaction](https://www.sqlite.org/lang_transaction.html); discussion: [Simon Willison on SQLITE_BUSY](https://simonwillison.net/tags/sqlite-busy)
- **Projections are disposable and rebuilt from the log.** Fowler's "Complete Rebuild" discards application state and replays the log on an empty application, which is our "projections disposable and rebuildable" rule. **Agree.** Source: [Event Sourcing (Fowler)](https://martinfowler.com/eaaDev/EventSourcing.html)
- **Tolerant Reader.** Fowler's pattern reads only the fields a consumer needs and ignores the rest, and has consumers share reader tests with producers. **Agree:** this matches our lenient reads that skip unknown event types. **Adopt:** a shared fixture corpus of events from every plugin that each reader's tests replay (consumer-driven contracts). Source: [Tolerant Reader](https://www.martinfowler.com/bliki/TolerantReader.html)
- **Weak schema and upcasting rather than strongly typed versions.** Greg Young's book covers weak schema (mapping, wrappers) and upcasting. The InfoQ report notes he advises against strongly typed versioning unless you can take the system down to upgrade it. **Agree:** this matches additive changes with one `user_version`. **Adopt:** name an upcast step (raw JSON to current shape, a pure function) as the sanctioned route for the rare non-additive change, rather than leaving it undefined. Source: [Versioning in an Event Sourced System](https://leanpub.com/esversioning/read); [InfoQ: Versioning in event sourcing](https://www.infoq.com/news/2017/07/versioning-event-sourcing)
- **Industry study: schema evolution and projection rebuilds are the pain points.** Overeem et al. studied 19 event-sourced systems. Event system evolution and rebuilding projections are among the five main challenges, and "never change events, add new ones" was cited often but rarely practised. **Agree:** this supports our additive-only rule. **Adopt:** measure projection rebuild time in CI on a large synthetic log, so a rebuild never becomes too slow to do. Source: [An empirical characterization of event sourced systems and their schema evolution](https://dspace.library.uu.nl/bitstream/1874/412217/1/1_s2.0_S0164121221000674_main.pdf); [InfoQ summary](https://www.infoq.com/news/2018/02/evolving-cqrs-event-sourcing/)
- **Upcasters as pure functions, with short streams.** Dudycz recommends mapping at the serialisation layer for small changes and upcasting middleware for bigger ones, and keeping streams short-lived. **Agree.** Source: [Simple patterns for events schema versioning](https://event-driven.io/en/simple_events_versioning_patterns/)
- **git-branchless: an event log in SQLite fed by git hooks.** git-branchless installs hooks that append to a SQLite event log, then replays the whole log at startup. Its wiki lists checkpoints as unimplemented, so long logs slow it down. **Agree:** this is close prior art for our design. **Adopt:** plan snapshots or checkpoints for projections before logs grow, rather than after. Source: [git-branchless Architecture wiki](https://github-wiki-see.page/m/arxanas/git-branchless/wiki/Architecture); [eventlog module docs](https://docs.rs/git-branchless-lib/latest/branchless/core/eventlog/index.html)

## 2. Git integration (CLI wrapper, custom refs, CAS, worktrees, imports)

- **`update-ref` compare-and-set, and multi-ref transactions.** The three-argument form verifies `<old-oid>` before writing; an all-zero old value means "must not exist". `--stdin` with `start`/`prepare`/`commit` updates several refs atomically, though a concurrent reader may see a subset. `-z` gives NUL-terminated input with no quoting. **Agree:** this matches our CAS leases. **Adopt:** use `--stdin -z` transactions whenever a lease and its state ref change together, instead of two separate CAS calls. Source: [git-update-ref](https://git-scm.com/docs/git-update-ref)
- **Gerrit NoteDb: review state stored in refs next to the code.** Gerrit keeps change metadata at `refs/changes/NN/<id>/meta`, which lets one snapshot of the refs back up code and metadata together. It can fuse code and meta updates into one atomic batch ref update, with tunable retry on lock contention. NoteDb has been Gerrit's only store since 3.0. **Agree:** this is the strongest proof that custom-ref state works at scale. **Adopt:** bounded retry-with-backoff on CAS lock failure, as Gerrit does. Source: [Gerrit NoteDb backend](https://gerrit.googlesource.com/homepage/+/613ad8f7599c754e1f1539b8b3ebebe29960f757/pages/gerrit/note-db.md)
- **git-bug: entities as operation logs in commit chains under `refs/<namespace>/<id>`.** Each operation pack is a blob, each edit adds a commit, Lamport clocks order operations, and state is derived by replay and never stored. **Agree:** this matches our event-sourced instincts. **Adopt:** git-bug's Lamport-clock-plus-id tie-break as the merge order if refs from two machines ever need merging, rather than wall-clock time. Source: [git-bug data model](https://www.github.com/MichaelMure/git-bug/blob/master/doc/model.md); [git-bug spec](https://github.com/git-bug/spec/)
- **git-appraise: git notes as line-oriented JSON with a mergeable strategy.** Reviews live under `refs/notes/devtools/*`, one JSON object per line, so notes merge automatically with `cat_sort_uniq`. Notes are not fetched by default (`refs/notes/*:refs/notes/*` must be added). **We differ:** we use plain refs rather than notes. **Adopt:** the line-JSON, sort-and-dedupe format for any state that must merge without conflicts, and document the explicit refspec our refs need, since custom refs are not fetched by default either. Source: [git-appraise README](https://github.com/tml/git-appraise/blob/master/README.md); [cat_sort_uniq commit](https://git.lorimer.id.au/gitweb.git/diff/a6a09095a08339afc8468d053ff978ed4662a1d5)
- **Shelling out vs gitoxide: jj moved fetch and push onto the git binary.** jj-lib has a `git_subprocess` module that pushes with `--force-with-lease` as a test-and-set. It sets a minimum git version (2.41 for `fetch --porcelain`, later 2.42) and became the default around jj 0.27. **Agree:** a mature Rust VCS chose the CLI for network operations. **Adopt:** check the git version at startup against a declared minimum, as jj does, and fail with a clear message. Source: [jj-lib git_subprocess.rs](https://docs.rs/jj-lib/latest/src/jj_lib/git_subprocess.rs.html); [Arch packaging note](https://gitlab.archlinux.org/archlinux/packaging/packages/jujutsu/-/commit/e04529c847cf927fe07e2d64293fd4769ce0d9b4)
- **Cargo keeps `net.git-fetch-with-cli` because of authentication.** Cargo's docs say libgit2 "is notably lacking in the realm of authentication when compared to the git command line". Gitoxide is still behind nightly `-Zgitoxide`. **Agree:** credentials, hooks and user config come free with the CLI. Source: [cargo fetch_with_cli](https://doc.rust-lang.org/stable/nightly-rustc/cargo/sources/git/utils/fn.fetch_with_cli.html); [gitoxide](https://www.Github.com/Byron/gitoxide)
- **jj's lock-free operation log.** jj records each operation as a content-addressed object pointing to a view, and treats concurrent operations as divergence to merge rather than taking locks. It admits that its Git backend is not fully lock-free. **We differ:** we serialise writers with CAS leases, which is simpler for short hook transactions. jj's design is the reference if leases become a bottleneck. Source: [jj concurrency doc (mirror)](https://git.joshthomas.dev/mirrors/jj/src/branch/main/docs/technical/concurrency.md)
- **Trailers: parse with git, not by hand.** `git interpret-trailers --parse` (`--only-trailers --only-input --unfold`) applies git's own rules for detecting a trailer block, including the 25% rule and configurable separators. **Adopt:** read trailers through `interpret-trailers --parse` (or `git log --format=%(trailers:...)`) inside the wrapper, so our parse matches git's. Source: [git-interpret-trailers](https://github.com/git/git/blob/c364b7ef51ec3af871754e7afdfd73e4bed6da56/Documentation/git-interpret-trailers.txt)
- **Worktrees share `refs/`, except `refs/worktree`, `refs/bisect` and `refs/rewritten`.** All `refs/*` are shared across worktrees except those three namespaces. Per-worktree config needs `extensions.worktreeConfig`. **Agree:** `refs/redkiln/...` in the common dir is visible to every lane, which leases need. **Adopt:** put lane-local scratch state under `refs/worktree/redkiln/...`, so lanes cannot collide on it. Source: [git-worktree](https://git-scm.com/docs/git-worktree)
- **Lock worktrees on removable or network storage.** `git worktree add --lock` avoids the race between `add` and `lock`, and prune skips locked entries. **Adopt:** create lanes with `--lock --reason redkiln-lane` and unlock on teardown, so `gc` never prunes a live lane. Source: [git worktree(1)](https://man.cx/git-worktree(1))
- **Monorepo import: `-s ours` merge plus `read-tree --prefix`.** The tomono script and gists use `merge -s ours --allow-unrelated-histories --no-commit` followed by `read-tree --prefix=dir/`, and warn never to squash the import. **Agree:** this is exactly our move recipe. Source: [tomono.sh](https://github.com/partikus-archive/tomono/blob/master/tomono.sh); [gist](https://gist.github.com/ixmatus/9a8dd88c167aa030196e1f3547f1e86d)
- **`git subtree add` is the built-in alternative.** It produces the same history-preserving merge in one command. **We differ:** our explicit `read-tree` keeps the second parent as the old tip, unchanged, and makes the rename a separate commit, which is what the migration plan's audit needs. Source: [git subtree monorepo (jvt.me)](https://jvt.me/posts/2018/06/01/git-subtree-monorepo)
- **Votruba: "keeping git history is not worth it".** His 7-step guide copies repositories in without history. **We differ, deliberately:** imported hashes must stay resolvable for records, decisions and Weigh-In ids. Source: [How to create monorepo from existing repositories in 7 steps](https://tomasvotruba.com/blog/2020/06/15/how-to-create-monorepo-from-existing-repositories-in-7-steps)
- **Josh: reversible history filtering.** Josh offers incremental, reversible projections of a monorepo subdirectory as a standalone repository (proxy or CLI). **Adopt (later):** a candidate for publishing a per-plugin mirror repository (for example to claude.ai's release repository) without hand-maintained splits. Source: [josh-project/josh](https://github.com/josh-project/josh)
- **Line endings: `* text=auto eol=lf`, CRLF exceptions, renormalize once.** The usual pattern sets LF everywhere, keeps CRLF for `*.bat`/`*.cmd`/`*.ps1`, runs `git add --renormalize .`, and recommends `merge.renormalize=true`. **Agree:** we already exempt `*.cmd`. **Adopt:** consider exempting `*.ps1` too (our launcher test is `test.ps1`), and add a CI check that no tracked text file contains CR. Source: [dsl-devkit PR #1314](https://github.com/dsldevkit/dsl-devkit/pull/1314); [Git and normalization of line endings](https://dev.to/kevinshu/git-and-normalization-of-line-endings-228j)

## 3. GitHub CI supply chain

- **Pin actions to full SHAs, read-only `GITHUB_TOKEN`, no untrusted code under `pull_request_target`.** GitHub's hardening guide recommends all three, plus intermediate environment variables for untrusted expressions and OIDC instead of long-lived secrets. **Agree** on all of them. Source: [Security hardening for GitHub Actions](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)
- **Workflow dependency lockfiles are coming.** The same guide now says workflow dependency lockfiles "supersede SHA pinning for repositories that adopt it". Secondary reports describe `.github/workflows/actions.lock`, generated by `gh actions-lock`, which also checks content hashes and covers transitive composite actions. **Adopt (evaluate):** SHA pins miss actions that composite actions pull in themselves. Trial the lockfile once it is documented, and keep SHA pins until then. Source: [Security hardening for GitHub Actions](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions); [DevX explainer](https://www.devx.com/coding/github-actions-workflow-lockfiles-explained/)
- **zizmor: static audit of workflows.** zizmor flags template injection (`${{ }}` inside `run:`), `artipacked` (checkout leaving credentials on disk, fixed with `persist-credentials: false`) and more, and auto-fixes some findings. **Adopt:** run zizmor in the `ci` workflow's plugins/rust path job. It turns the hardening guide into a check, which fits our "rules are checked, not only written" charter. Source: [Securing our GitHub Actions workflows with zizmor (Packagist)](https://blog.packagist.com/securing-our-github-actions-workflows-with-zizmor/); [zizmor intro](https://blog.yossarian.net/2024/10/27/Now-you-can-have-beautiful-clean-workflows)
- **OpenSSF Scorecard.** Scorecard scores Pinned-Dependencies, Token-Permissions, Branch-Protection, Dangerous-Workflow and more, and GitHub's guide endorses it. **Adopt:** run Scorecard periodically as an external audit that our pins and permissions have not drifted. Source: [OpenSSF Scorecard for .NET/NuGet (check descriptions)](https://devblogs.microsoft.com/nuget/openssf-scorecard-for-net-nuget/)
- **Artifact attestations reach SLSA Build L2, and L3 through reusable workflows.** `actions/attest-build-provenance` (now `actions/attest`) binds artifact digests to SLSA provenance, verified with `gh attestation verify` (including `oci://` images). Private repositories need GitHub Enterprise Cloud. **Adopt:** attest release binaries and the GHCR artifacts, if our plan allows. Otherwise use the cosign route below. Source: [Using artifact attestations](https://docs.github.com/actions/security-guides/using-artifact-attestations-to-establish-provenance-for-builds); [attest-build-provenance](https://github.com/actions/attest-build-provenance)
- **SLSA levels as the vocabulary.** L1 means provenance exists, L2 means signed provenance from a hosted builder, L3 means a hardened builder. v1.2 is current. **Adopt:** state our target level in the release runbook. We are at roughly L1 today (digest pinning without signed provenance). Source: [SLSA v1.0 levels](https://slsa.dev/spec/v1.0/levels)
- **Sign ORAS artifacts with cosign keyless, by digest.** Sigstore documents pushing a generic artifact with ORAS and then `cosign sign` on its digest. Keyless mode uses Fulcio and Rekor through GitHub OIDC. **Adopt:** pinning by digest proves integrity but not origin; a signature adds the origin and costs no secrets. Source: [Signing other types (Sigstore)](https://docs.sigstore.dev/cosign/other_types); [cosign](https://github.com/sigstore/cosign/)
- **The aggregate `ok` check is standard practice.** GitHub's docs confirm that a path-filtered workflow leaves a required check "Pending". The community answer is a final job that `needs` everything and passes on success or a legitimate skip (`re-actors/alls-green`, with `allowed-skips`). **Agree:** this is our `ci / ok`. Source: [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks); [alls-green](https://www.github.com/marketplace/actions/alls-green)
- **Pin required checks to the GitHub App that must report them.** Required checks can be restricted to a specific app (`app_id`), so a status from another app or a manual commit status cannot satisfy them. **Adopt:** pin `ok` to GitHub Actions, and the verdict check to our verdict App, in the `main` ruleset. Without it, any token with `statuses: write` can spoof the gate. Source: [Ensure required status checks provided by the intended app](https://github.blog/changelog/2021-11-30-ensure-required-status-checks-provided-by-the-intended-app/)
- **Short-lived, narrowed App tokens.** Installation tokens expire after an hour, can be scoped to fewer repositories and permissions at mint time, and can be revoked early with `DELETE /installation/token`. **Adopt:** mint per job, narrow to the one repository and the permissions the step needs, and revoke in an `always()` step. Source: [gh-token](https://github.com/Link-/gh-token); [fnox GitHub App leases](https://fnox.jdx.dev/leases/github-app.html)
- **Dependabot cooldown and groups.** Dependabot supports `cooldown` (`default-days`, per-semver days) and `groups`, while security updates still bypass the schedule. **Adopt:** a few days of cooldown on cargo and github-actions updates guards against freshly compromised releases. Group action bumps to cut noise. Source: [Tame Dependabot (GitHub blog)](https://github.blog/security/application-security/tame-dependabot-group-your-updates-slow-the-cadence-keep-security-fast/); [Apache Infra Dependabot guide](https://infra.apache.org/dependabot.html)
- **cargo-deny's four checks.** cargo-deny covers advisories, bans (including duplicate versions), licenses and sources. Ignored advisories still print a note. **Agree.** Source: [cargo-deny docs](https://docs.rs/cargo-deny)
- **cargo-auditable: binaries that list their own dependencies.** It embeds a compressed dependency list (under 4 kB) in a `.dep-v0` section, which `cargo audit bin`, trivy, grype and osv-scanner can read. **Adopt:** build release binaries with `cargo auditable build`, so binaries already installed in users' `libexec/` folders can be checked against advisories that appear after release. Source: [cargo-auditable](https://github.com/rust-secure-code/cargo-auditable)

## 4. Distribution (libexec binaries, launchers, per-package tags)

- **dist (cargo-dist) is the reference Rust release pipeline.** It builds per-target archives including musl, generates shell and PowerShell installers, and attests artifacts with GitHub attestations. **We differ:** a plugin must carry its binaries inside its own folder, and claude.ai has no installer step. **Adopt:** its manifest and checksum conventions (`sha256` beside each archive), and possibly use dist only as the builder, then copy outputs into `libexec/<target>/`. Source: [cargo-dist v0.33.1 release](https://github.com/axodotdev/cargo-dist/releases/tag/v0.33.1)
- **ripgrep: one create-release job, a build matrix, musl, attested provenance.** ripgrep's release workflow creates the release once, builds musl targets with `cross`, and attests provenance. Its project switched to jemalloc on musl because musl's allocator slowed it down. **Agree** on musl static builds. **Adopt:** benchmark our hook hot paths on musl, and if allocation matters, use a faster allocator (an H-16 dependency decision). Source: [ripgrep release.yml (mirror)](https://gitcode.com/GitHub_Trending/ri/ripgrep/blob/master/.github/workflows/release.yml); [ripgrep #2739](https://www.github.com/BurntSushi/ripgrep/issues/2739); [buildroot note on jemalloc](https://buildroot.uclibc.org/lists/buildroot/2021-August/306529.html)
- **Astral (uv) installers: versioned URLs and opt-outs.** uv's installer can be pinned by putting the version in the URL, inspected before running, and told not to edit PATH (`INSTALLER_NO_MODIFY_PATH`). **We differ:** we never put binaries on PATH. That matches our decision to keep binaries out of `plugin/bin/`. Source: [uv installation](https://docs.astral.sh/uv/getting-started/installation/)
- **release-plz: per-package tags `{{ package }}-v{{ version }}`, a changelog per package directory, release PRs.** Its default tag for a workspace is `<package>-v<version>`. `git_only` handles `publish = false` crates. Each package's `CHANGELOG.md` collects commits that touch its directory. `release_always = false` releases only when a release PR merges. **Adopt (evaluate):** our `rk-<plugin>--v<version>` scheme fits through `git_tag_name`, and its path-scoped changelogs and release PRs could replace a hand-written xtask. **We differ** on the separator (`--`), which we keep so tags are unambiguous for plugin names that contain hyphens. Source: [release-plz configuration](https://release-plz.dev/docs/config)
- **git-cliff per-package changelogs by path.** cpp-linter-rs moved to per-crate tags with per-package changelogs assigned by file path. **Agree:** this is the same model as our per-package `CHANGELOG.md`. Source: [cpp-linter-rs PR #302](https://github.com/cpp-linter/cpp-linter-rs/pull/302)

## 5. Rust CLI design and workspace policy

- **clig.dev: stdout for data, stderr for messages, `--json` for scripts, additive changes.** clig.dev says to keep changes additive, warn before breaking ones, and steer scripts to `--json`/`--plain`. It also covers documented non-zero exit codes, configurable timeouts, crash-only recovery, `NO_COLOR` and `--no-input`. **Agree.** **Adopt:** honour `NO_COLOR`, and treat "re-running resumes" (crash-only) as a hook design rule. Source: [Command Line Interface Guidelines](https://clig.dev/)
- **Version the JSON and make the caller ask for a version.** Cargo says `cargo metadata` "is stable and versioned" and that callers "should pass `--format-version` flag explicitly". For build messages it recommends dispatching on a `reason` tag and parsing only lines that start with `{`. **Adopt:** add a `--format-version` (or schema-id) argument to `--json` commands so a consumer pins the contract, and keep a `reason`/`kind` discriminator on every streamed line. Source: [Cargo external tools](https://doc.rust-lang.org/cargo/reference/external-tools.html)
- **gh: `--json <fields>` with `--jq`/`--template`.** gh makes callers name the fields they want and filters on the CLI side. **Adopt (optional):** field selection keeps outputs small for agent contexts. Source: [gh help formatting](https://cli.github.com/manual/gh_help_formatting)
- **kubectl: name the group and version explicitly.** kubectl warns that without an explicit group and version it uses the server's preferred one, and that structures change between versions. **Agree:** this matches our `schema` field (`<name>/<n>`) in every document. Source: [kubectl resource printing](https://kubectl.docs.k8s.io/guides/resource_printing/fields/)
- **12-factor CLI.** Dickey's factors favour flags over positional arguments, good in-CLI help, and errors treated as a normal output. **Agree.** Source: [12 Factor CLI Apps](https://jdxcode.medium.com/12-factor-cli-apps-dd3c227a0e46)
- **thiserror for libraries, anyhow for applications.** anyhow's own docs and Google's Comprehensive Rust say `anyhow::Error` is a poor choice for a library's public API. **Agree:** this is our H-09. Source: [anyhow](https://docs.rs/crate/anyhow); [Comprehensive Rust: thiserror and anyhow](https://google.github.io/comprehensive-rust/error-handling/thiserror-and-anyhow.html)
- **Rust API Guidelines: meaningful errors and future-proof types.** The checklist includes C-GOOD-ERR, C-SEALED, C-STRUCT-PRIVATE and C-NEWTYPE-HIDE. **Agree.** **Adopt:** `#[non_exhaustive]` on public error enums in kit and contract crates, so adding a variant is not an API break across plugin packages that update separately. Source: [Rust API Guidelines checklist](https://rust-lang.github.io/api-guidelines/checklist.html)
- **`#[expect(lint, reason)]` and the `allow_attributes` lints.** Rust 1.81 stabilised `expect` with reasons and added `clippy::allow_attributes` and `allow_attributes_without_reason`. **Agree:** they enforce H-05 mechanically. Make sure both lints are denied in the workspace table. Source: [Announcing Rust 1.81.0](https://blog.rust-lang.org/2024/09/05/Rust-1.81.0/)
- **The xtask pattern.** cargo-xtask puts repository automation in a workspace crate run through a cargo alias, and Cargo itself uses it. **Agree.** Source: [cargo-xtask](https://redirect.github.com/matklad/cargo-xtask)
- **matklad: flat `crates/`, virtual manifest, internal crates at `0.0.0`.** matklad argues one flat level scales to about a million lines. Published crates go in a separate folder, so a check can confirm they do not depend on internal ones. **We differ:** we nest one level (`crates/core`, `crates/kits`, `crates/<plugin>`), because the layer rules are the point. `cargo xtask layers` is exactly the dependency-direction check matklad suggests. Source: [Large Rust Workspaces](https://matklad.github.io/2021/08/22/large-rust-workspaces.html)
- **Clippy has no built-in baseline; the ratchet pattern comes from other tools.** An LLVM 2026 talk describes a baseline file in the repository that flags only new warnings and ratchets down as warnings are fixed. A SAST guide warns that matching findings by line number makes edits above them look new, so fingerprints are needed. **Agree:** this is temper's `baseline --check`. **Adopt:** make sure fingerprints do not depend on line numbers, and re-baseline on toolchain bumps, since a new clippy can add findings. Source: [LLVM dev meeting 2026 talk](https://www.llvm.org/devmtg/2026-04/slides/technical_talk/technical_talk_bartolomeo.pdf); [Fail only on new findings](https://safeguard.sh/resources/blog/fail-only-on-new-findings-sast-ratchet)
- **The MSRV-aware resolver is the default in edition 2024.** Rust 1.84 stabilised `incompatible-rust-versions = "fallback"`, and edition 2024 implies `resolver = "3"`. **Agree:** with MSRV equal to the pin, this is mostly moot. **Adopt:** set `resolver = "3"` explicitly in the virtual workspace, as the edition guide requires. Source: [Edition guide: Cargo resolver](https://www.rustmax.net/library/edition-guide/rust-2024/cargo-resolver)
- **cargo-hack `--feature-powerset`.** It deduplicates equivalent feature sets, takes `--depth` to cap combinations, and pairs with `--no-dev-deps`. **Agree.** **Adopt:** `--depth 2` once a crate grows several features. Source: [cargo-hack](https://github.com/taiki-e/cargo-hack)
- **cargo-machete is fast but imprecise.** It searches source text, so expect false positives, which go in `package.metadata.cargo-machete.ignored`. cargo-udeps (nightly, compiled) and cargo-shear (syn-based) are the alternatives. **Agree:** fine for CI. Document each ignore entry. Source: [cargo-machete (Bouvier)](https://blog.benj.me/2022/04/27/cargo-machete); [cargo-shear](https://docs.rs/crate/cargo-shear/1.12.0)
- **cargo-semver-checks for the contract crates.** It runs lints over before-and-after rustdoc JSON and exits non-zero on a break. **Adopt:** run it on `*-contract` and kit crates against the last `rk-*` tag. Under per-package versioning, an API break in a contract crate is exactly what H-16 wants caught. Source: [Toward fearless cargo update](https://predr.ag/blog/toward-fearless-cargo-update/)

## 6. Cross-platform (Windows, Git Bash, processes)

- **Rust refuses `.cmd`/`.bat` arguments it cannot escape (CVE-2024-24576).** Since 1.77.2, `Command` returns `InvalidInput` when it cannot escape an argument safely for a batch file. `raw_arg` bypasses the escaping. **Adopt:** our `.cmd` launchers are batch files. Have Rust code invoke the `.exe` directly, never the launcher, treat `InvalidInput` as a typed error, and ban `raw_arg` in review. Source: [Rust security advisory CVE-2024-24576](https://blog.rust-lang.org/2024/04/09/cve-2024-24576/)
- **Git Bash rewrites arguments that look like POSIX paths.** MSYS converts arguments starting with `/` to Windows paths (`-L/regex/`, `--upload-pack=/x`). `MSYS_NO_PATHCONV=1` or `MSYS2_ARG_CONV_EXCL='*'` disables this. An open Claude Code issue reports `ref:.path` arguments being mangled. **Adopt:** have the sh launcher export `MSYS_NO_PATHCONV=1` before exec on MSYS, and add `<ref>:<path>` arguments to the launcher's Windows tests. Source: [KBEC-00420 Stopping path conversion for Git Bash](https://docs.cloudbees.com/docs/cloudbees-cd-kb/latest/cloudbees-cd-kb/kbec-00420-stopping-path-conversion-for-git-bash); [Claude Code issue 91771](https://claudeissues.com/issue/91771-bug-windows-git-bash-git-ref-dot-path-arguments-silently-rewritten-so-a-mangled)
- **Long paths: Rust handles them, git needs `core.longpaths`.** Rust 1.58+ adds the `\\?\` prefix to absolute paths automatically, but relative paths stay limited to MAX_PATH, and `canonicalize` returns verbatim paths that confuse other tools. Git for Windows needs `core.longpaths=true`, which is off by default. **Adopt:** pass absolute paths to the filesystem, avoid `canonicalize` for display or comparison, and set `-c core.longpaths=true` in the git wrapper on Windows. Source: [rust-lang/rust #89174](https://github.com/rust-lang/rust/pull/89174); [git-for-windows core.longpaths commit](https://github.com/git-for-windows/git/commit/56c77f3bb4e5595ac554ce2713273d81b3449cc4)
- **tokio `kill_on_drop` kills only the direct child, best effort.** Tokio reaps dropped children in the background with no timing guarantee and recommends awaiting `wait()`/`kill()`. It says nothing about descendants. processkit shows the fix: a Windows Job Object with `KILL_ON_JOB_CLOSE`, the child created suspended and then assigned to the job, and process groups with SIGTERM then SIGKILL on Unix. **Adopt:** supervise `git` and `claude -p` children with a process group or Job Object, so a timeout kills the whole tree. With only `kill_on_drop`, grandchildren survive. Source: [tokio::process::Command](https://docs.rs/tokio/latest/tokio/process/struct.Command.html); [processkit group.rs](https://docs.rs/crate/processkit/latest/source/src/group.rs)
- **POSIX lock quirks matter on every platform.** The SQLite note on `close()` dropping locks applies whenever a helper opens the database file (backup, hashing, a sync client). **Agree:** this supports keeping one owner of the ledger file per process. Source: [How To Corrupt An SQLite Database File](https://www.sqlite.org/howtocorrupt.html)
